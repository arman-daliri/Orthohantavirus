Orthohantavirus pipeline · session write-up

What I changed, why, and how I knew it was wrong

Seven defects in all_hanta.py, found by reading the code and measuring the pipeline's own output. Ends at commit b8f5f0c, pushed to main.

This is a record of one working session, written so you can check my reasoning rather than take it on trust. Every claim below has a number behind it, and every number came from running the pipeline against the real 15,991-record package.

Where we started

The repo was at 48095e0, on main, working tree clean apart from an untracked __pycache__/. You first asked whether main and v2 were identical — they were, both pointing at the same commit with an empty diff.

You then asked me to run ultrareview from the command line. I couldn't: that command is user-triggered and billed, so it has to come from you, and there's no --non-interactive --output json form of it. Rather than stop there, I did the review directly — read all 2,420 lines of all_hanta.py, ran the pipeline, and checked its claims against its own output.

How I looked for bugs

1

Read the whole file first

No skimming for patterns. A pipeline like this fails at the seams between functions — a constant that disagrees with the comment above it, a tier of a cascade that can never be reached — and you only see those by holding the whole thing in view at once.

2

Run it before touching anything

I ran the pipeline into a scratch directory, not into output/, so your committed artifacts stayed untouched while I worked. That run became the baseline every later number is measured against.

3

Check the code's claims against its own output

This codebase documents itself with measured figures — "15,491 records have isolate.name", "3,393 are exact resubmissions". That's a gift: every one of those is a falsifiable claim. I compared them to ortho_summary.json, and the first real bug fell out of a distribution that didn't look right.

4

Measure a fix before committing to its direction

Twice this changed my mind — once about how aggressively to normalise labels, once about whether to "fix" a constant at all. Details in both places below.

The defects I found

Defect 1 · corrupted a published signal

Cross-species flags fired on meaningless labels

flag_cross_species_labels() looks for one isolate label whose segments NCBI assigned to two different species. That's a genuinely valuable signal, and the pipeline advertises it as its one metadata fact, not inference — it's the only term besides case-fatality that feeds surveillance_priority, at weight 1.5.

The function treated any non-empty label as a globally unique sample identifier. But submitters number their own samples independently. So I dumped the flagged rows and sorted by label length:

LabelSpecies it "spans"
2PUUV, SEOV, SNV, CBNV, unclassified
1SNV, CBNV
43PUUV, unclassified
Hu39694ANDV, unclassified

Five unrelated isolates each named 2 were being reported as one sample spread across five species. 31 of the 70 flagged isolates carried a purely numeric label. That noise was inflating the surveillance ranking the table exists to produce.

The fix

A new predicate, is_cross_study_label(): a label only counts as a cross-submission identity if it has at least four alphanumeric characters and isn't a bare number.

def is_cross_study_label(label: str) -> bool:
    key = normalize_key_text(label).replace(" ", "")
    return len(key) >= CROSS_STUDY_LABEL_MIN_CHARS and not key.isdigit()

70 → 34 flags. Every survivor is a specific label: Hu39694, 23723MA, YN-Rn-014/China/2021, Deaf Smith County, Texas, May 1995.

Why grouping isn't subject to the same rule. A grouping key also contains the species, and any over-merge it causes surfaces as metadata_conflict — which happens for only 4 of 254 numeric-label isolates. A cross-species check has no such backstop by construction, and its output reaches the risk score. Same-looking problem, different blast radius.

Defect 2 · dead code hiding a data loss

Label normalisation never reached a grouping decision

normalize_key_text() exists, with a docstring explaining it's there so PUUV/Foo-01 and puuv foo 01 agree. build_group_key() has a five-tier cascade, and tier 3 is named tier_3_species_isolate_normalized.

But the tier counts in ortho_summary.json showed only three tiers ever firing:

tier_2_species_isolate    15404
fallback_accession_only     500
tier_1_biosample_isolate     87

Tier 2 keys on species + raw isolate name and claims 15,404 of 15,991 records — so it short-circuits tier 3 for every record that has an isolate name. The normaliser never influenced a grouping decision at all. Tiers 4 and 5 key on strain, which in this package only ever arrives from BioSample (87 records), so they never fire either.

The cost: 52 isolates were split across spelling variants of their own label.

Variant AVariant B

The fix, and the measurement that shaped it

Tier 2 now normalises. But how to normalise mattered more than I expected. The original function deleted every non-alphanumeric character. I tested both that and a softer version that collapses separator runs to a single space:

StrategyPairs mergedOf which unsafe
Delete separators12068
Collapse to space520

Deleting separators merges more, but 68 of those pairs differ only at a digit boundary — 11-4 vs 114, B-1 vs B1, Aa-08-1111 vs Aa08/1111. Those are not safe to call the same sample. I took the softer form and changed normalize_key_text to match, which also makes the cross-species check stricter.

9,904 → 9,852 isolates, and 222 → 223 complete triplets. That extra triplet is real: merging HV 97021050 into HV-97021050 reunites NC_034552 / NC_034553 / NC_034566, a complete RefSeq S/M/L set that had been split in two.

I verified 11-4 stayed apart from 114 afterwards: 16 groups before, 16 after.

Defect 3 · a check that couldn't fail

The integrity log always read "N/N verified"

report_checksums() computed one number and printed it on both sides of a ratio:

checked = sum(1 for r in results if r.matched_form == "raw")
logging.info("Integrity: %s/%s files verified", checked, checked)

A file shipped without a published checksum is recorded as unlisted and skipped — but it vanished from both numerator and denominator, so the line reported perfect verification no matter what. It now counts verified files against files that md5sum.txt actually covers, and says out loud how many were shipped without one.

Defect 4 · misreported scale

Load logs double-counted every record

Startup reported annotation_report: 31982 indexed accessions and genomic: 31982 entries for files that hold 15,991 records each. Both indexes file every record twice — once under its versioned accession, once under the bare base — so len(index) is roughly double the record count. Anyone sanity-checking the load against the source files would have seen a 2× discrepancy and gone looking for a bug that wasn't there.

Added indexed_record_count(); the line now reads 15991 records (31982 index keys).

Defect 5 · latent

Two taxonomic orders disagreed between tables

HOST_ORDER_ROLE maps Soricomorpha and Insectivora — superseded names for Eulipotyphla still found in older NCBI lineages — to the shrew/mole role, with a comment saying exactly that. HOST_ORDER_RISK_PRIOR omitted both, so the same shrew would read low risk in one table and unknown in another. No records in this package hit it, so it's latent rather than active, but it's a trap for the next dataset. Added.

Then you ran the real ultrareview

It returned three findings, all severity nit, and its scope was much wider than my diff — 17 files, because local main was five commits ahead of origin/main, so it reviewed the whole branch rather than just my changes. I checked each finding against the code and the data before acting. All three were factually correct. I fixed two as described and deliberately fixed the third in the opposite direction.

Cloud finding · accepted

verify_inputs couldn't see a missing file

It walked the data directory, so a file listed in md5sum.txt but deleted from the checkout produced no result and passed the gate in silence. resolve_inputs hard-fails on the four required reports, so only the optional FASTAs were exposed — but parse_fasta treats a missing file as an empty index, so a deleted protein.faa would log a clean bill of health and ship a quietly smaller ML matrix instead of stopping.

I added a reconciliation pass over the expected map, then proved it by deleting protein.faa from a scratch copy of the package:

ERROR | CHECKSUM MISMATCH protein.faa
ERROR |     expected (NCBI): d5b958b81830bbff4f98dac75fca112a
ERROR |     observed (disk):
ERROR |     diagnosis      : listed in NCBI's md5sum.txt but not present
                             on disk; the package is incomplete.

Aborting: 1 input file(s) do not match NCBI's published checksums.

Before the fix, that same scenario printed Integrity: 6/6 files verified and carried on.

Cloud finding · accepted

The tracked log had been accumulating for three weeks

configure_logging() built its handler as logging.FileHandler(log_file, encoding="utf-8"). FileHandler defaults to append mode. Since output/ortho_pipeline.log is tracked in git, every run left it dirtier: 428 lines spanning three weeks, carrying absolute paths from two different machines — including a collaborator's home directory and username — plus stale references to ortho_virus_table.parquet, a table that no longer exists.

One character of fix: mode="w". The log is now 33 lines, one run, zero foreign paths. I also added a .gitignore for __pycache__/, .venv/ and output/*.log.

Cloud finding · fixed the other way

The L-segment range disagreed with its own citation

The comment and the README both cite ICTV segment sizes as S 1.2–2.1 kb, M 3.4–3.8 kb, L 6.5–6.6 kb. The constant says:

SEGMENT_LENGTH_RANGE = {"S": (1200, 2100), "M": (3400, 3800), "L": (6300, 6800)}

S and M match exactly; L is wider at both ends. A real inconsistency. The obvious move is to tighten the constant to match the citation — so I measured what that would do before doing it.

Consequence of tightening L to 6500–6800Records affected
Length-heuristic L calls lost1 (a 6,462 nt record)
New length_anomaly flags gained0

A 6,462 nt sequence is unambiguously an L segment. Tightening the constant would have demoted it to unresolved and improved nothing. The constant was right and the documentation was wrong, so I documented the widened bound and the reason for it in both the code comment and the README, and left the behaviour alone.

This is the part worth generalising: a finding can be entirely accurate about what is inconsistent and still point at the wrong file to change. The measurement decides.

The one number that went up, explained. metadata_conflict rising from 169 to 182 is not a regression — it's the flag doing its job. Merging two spellings of one label pulls together submissions that recorded the same sample at different date granularity (2019 vs 2019-08-14), and the pipeline correctly says so. What this means for anything downstream

One consequence deserves flagging on its own, because it will break things silently otherwise:

isolate_key strings changed for nearly every tier-2 row. The key embeds the isolate label, and that label is now normalised, so the string itself is different. All output tables were regenerated together so they remain internally consistent — but any notebook, cache or saved join that holds old isolate_key values will silently fail to match. Re-derive them from the new tables.

Pushed

277ea1b..b8f5f0c to github.com:arman-daliri/Orthohantavirus. Six commits went up, not one — origin/main had been five behind, so the two pipeline rewrites and the earlier v2/v3 commits were published at the same time.

A correction I made along the way. Early in the session I described local main and origin/main as having diverged, on the basis that their SHAs differed. That was wrong. git rev-list --left-right --count returned 0 6 — origin/main was a strict ancestor, so main was simply six commits ahead, nothing behind. Differing SHAs don't distinguish "behind" from "diverged"; only the ancestry check does.

Still open

  • The old absolute paths are in pushed history. mode="w" stops future leaks and the current tip is clean, but commits from f52d35e onward still contain the accumulated log, including a collaborator's home directory. Removing that means a history rewrite (git filter-repo plus a force-push, which changes every SHA for anyone who has cloned). Worth doing only if the repo is public and that exposure matters to the person named.
  • output/ortho_pipeline.log is still tracked. A .gitignore rule has no effect on a file already in the index. It's clean and small now, but if you'd rather it left version control entirely: git rm --cached output/ortho_pipeline.log.
  • The merged branch still exists. git branch -d fix/grouping-normalization-and-integrity when you want it gone.
  • Tiers 4 and 5 of the grouping cascade remain unreachable with this package, because strain only ever arrives from BioSample. I left them in — a different NCBI package could populate strain and make them live. Worth knowing they're currently untested by real data.

Two habits worth stealing

Distributions catch what code review misses. Defect 2 was invisible in the source — the cascade reads perfectly. It only appeared as a tier-count table with three rows where five were expected. If a function branches on data, print how often each branch fires.

Measure before you accept the obvious fix. On the L-segment range the obvious fix would have made the pipeline slightly worse. On label normalisation the aggressive option merged more than twice as many pairs and would have quietly fused distinct samples. In both cases the direction was decided by a number, not by which side looked more like a bug.
